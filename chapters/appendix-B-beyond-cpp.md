# Appendix B — Beyond C++: Alternative Languages for Low-Latency

> **Relates to:** Ch. 20 (the cost of abstractions), Ch. 23–24 (allocation / GC-free memory management), Ch. 30–36 (concurrency / memory model), Ch. 46 (warm-up — directly relevant to JIT warm-up), Ch. 1 (tail latency — GC pauses *are* tail events). This appendix steps outside C++ to ask what other languages offer the hot path, and where each fits the latency tiers of the book.

This book is C++-centric for good reasons — it gives you zero-cost abstractions (Ch. 19–20), manual memory control (Ch. 23–24), direct hardware access (Ch. 28–29, intrinsics), a mature low-latency ecosystem (Ch. 55, 58, 61, 62), and *no runtime between you and the machine*. But C++ is not the only language that can hit the hot path, and the choice is increasingly nuanced. This appendix surveys the alternatives by the one question that matters for low latency: **what stands between your code and deterministic, single-digit-microsecond (or nanosecond) behavior?** The decisive dividing line is the **garbage collector** — a runtime that can pause your thread at a time it chooses is fundamentally at odds with tail-latency control (Ch. 1), and that single fact partitions the language landscape.

The framing throughout: **match the language to the latency tier** (the same tiering as Ch. 67–69 and Appendix A). The tick-to-trade hot path (Ch. 53, 55, 58, 61, 62, 76) demands a non-GC, ahead-of-time-compiled, manual-memory language — C++, Rust, C, or Zig. The surrounding tiers (research, backtesting, monitoring, control plane, UIs) can use whatever is productive, GC and all. The art is putting the boundary in the right place and interoperating cleanly across it (B.5).

## B.1 Rust (ownership, `unsafe`, no GC, fearless concurrency)

Rust is the most serious alternative to C++ for the hot path — it shares C++'s core proposition (no GC, zero-cost abstractions, AOT-compiled to native via LLVM, direct hardware access) while adding **compile-time memory safety**:

- **No GC, no runtime pauses.** Rust manages memory with **ownership and borrowing** checked *at compile time* — RAII-style deterministic destruction (like C++'s, Ch. 23–24), no garbage collector, no runtime pauses (Ch. 1). The steady-state hot path can be allocation-free (Ch. 23–24) exactly as in C++. This is the property that puts Rust on the hot-path side of the GC line.
- **Memory safety without a runtime cost.** The borrow checker enforces — at compile time, zero runtime cost — the exact bug classes that plague C++'s zero-allocation/arena designs (Ch. 72.4.2): use-after-free, data races, buffer overflows, iterator invalidation. For a domain where UB is a vulnerability *and* a latency hazard (Ch. 72.2.2), getting those guarantees *for free at compile time* is compelling — Rust eliminates by construction much of what Ch. 40/72 spends effort detecting.
- **"Fearless concurrency."** The same ownership system statically prevents data races (Ch. 30–33): the type system tracks `Send`/`Sync`, so shared mutable state across threads without synchronization simply won't compile. The lock-free structures of Ch. 34–37 are buildable in Rust (with `std::sync::atomic`, the same C++-derived memory model — Ch. 30), and the compiler catches the sharing bugs ARM would otherwise expose (Appendix A.1).
- **`unsafe` for the last mile.** The hot-path tricks that *need* to bypass the checker — raw pointers off the wire (Ch. 53), custom allocators (Ch. 24), intrinsics/SIMD (Ch. 29), `mmap`/device access (Ch. 26) — go in `unsafe` blocks, which *disable specific checks* while keeping them visible and auditable. This is honest: the dangerous code is *marked*, not pervasive (contrast C++, where every line has C++'s freedoms). The discipline: keep `unsafe` small, wrapped in safe abstractions, and concentrated at the hardware boundary.
- **The low-latency ecosystem is younger but real.** Kernel bypass (DPDK bindings, `io_uring` via crates), lock-free crates (`crossbeam`), SIMD (`std::simd`, portable), and HFT-in-Rust shops exist. It lags C++'s decades of trading-specific libraries (FIX/SBE decoders, vendor NIC SDKs — Ch. 55, 62 are often C/C++ APIs), but the gap narrows. The verdict: **Rust is a credible hot-path language**; the trade-off is ecosystem maturity and team familiarity vs. compile-time safety that directly attacks Ch. 72's bug classes.

## B.2 C and Zig

Two lower-level options, at opposite ends of "maturity vs modern ergonomics":

- **C** — the lingua franca beneath everything. The OS, the NIC drivers and vendor SDKs (Ch. 55, 62 — Solarflare `ef_vi`, DPDK, `libexanic`), `liburing` (Ch. 48), and most of the kernel-bypass stack expose **C APIs**. C is maximally simple, predictable, and transparent (what you write is close to what runs — Ch. 4), with no GC and total manual control. But it lacks C++'s zero-cost abstractions (Ch. 19–20 — no templates/RAII/`constexpr`), so the abstraction-building that makes a large low-latency codebase maintainable is on you, by hand. In practice C shows up as the *interop layer* (B.5) and in the vendor SDKs you call, rather than as the language you write a modern strategy engine in — most HFT C++ *is* C++-not-C precisely for the abstractions. C remains essential to *understand and interface with*, even when you write C++.
- **Zig** — a modern systems language aiming at "C, but better": no hidden control flow, no hidden allocations (allocators are explicit and passed in — a natural fit for Ch. 24's arena/pool discipline), `comptime` (compile-time execution rivaling C++ `constexpr`/templates, Ch. 18 — but simpler), no GC, AOT-compiled, and excellent C interop (Zig can compile C, and call/be-called by C trivially — B.5). For low latency, Zig's **explicit-allocator** model is philosophically aligned with this book (you can't accidentally allocate on the hot path — Ch. 23 — because allocation is always explicit and passed-in), and its transparency aids the Ch. 4 "read the machine" discipline. The trade-off: Zig is young (pre-1.0 as of writing), with a small ecosystem and no trading-specific libraries — an interesting choice for greenfield systems-level components, not yet a mainstream HFT hot-path language. Worth watching; its allocator-explicit, no-hidden-cost design is the right shape for this domain.

## B.3 The case against managed runtimes (Java/C#/Go GC pauses and JIT warm-up)

Managed runtimes — Java/JVM, C#/.NET, Go — are productive, safe, and ubiquitous, and they are **fundamentally hostile to the tick-to-trade hot path** for two reasons rooted in the whole book:

- **GC pauses are tail-latency events (Ch. 1).** A garbage collector reclaims memory *when it decides to*, and a collection can **stop your thread** — for microseconds (modern low-pause collectors) to *milliseconds or more* (a full GC). On a path with a sub-microsecond budget where the *tail* is the product (Ch. 1), an unpredictable multi-millisecond pause is catastrophic: it's a p99.9 outlier you can't control, arriving at the worst time (allocation pressure peaks during the open burst — Ch. 53). Even "low-pause" collectors (ZGC, Shenandoah, Go's concurrent GC) trade pause length for throughput and *still* have pauses and read/write barriers (a per-access cost). The fundamental mismatch: **the GC owns the timing of your tail, and you don't.**
- **JIT warm-up violates Ch. 46.** JVM/.NET compile hot methods *at runtime* after observing them interpret — so the *first* executions are slow (interpreted), then progressively optimized, with possible *deoptimization* (falling back to interpreter) mid-run. This is exactly the cold-start problem of Ch. 46, baked into the runtime: your first real ticks run interpreted/unoptimized, precisely when (market open) you can least afford it, and a deopt can re-introduce a stall mid-session. C++/Rust/C/Zig are AOT-compiled — *fully optimized before the first tick* (the Ch. 46 warming is about caches/TLB, not code compilation).
- **Less control over layout/allocation.** Managed runtimes hide object layout (Ch. 9 — header words, no control over padding/SoA), make stack-vs-heap opaque, and allocate implicitly (every `new` is GC pressure). The data-oriented, cache-aware, zero-allocation techniques of Parts II/IV are *fought* rather than expressed.
- **Go specifically:** simpler than the JVM, fast compile, good concurrency *ergonomics* (goroutines) — but it has a GC (concurrent, low-pause, but present, with write barriers) and a runtime scheduler that can preempt goroutines. Go is excellent for *services around* the hot path (control plane, tooling, networked infrastructure) but the GC keeps it off the order path, same as the JVM.

The conclusion is not "managed runtimes are bad" — they're great for the surrounding tiers — but **the order path needs a language whose memory timing you control**, and a GC by definition takes that control away.

## B.4 Taming the JVM: allocation-free Java, off-heap, Azul/Zing, GraalVM native-image

And yet — there *are* HFT shops running Java on latency-sensitive paths, because the JVM's productivity, libraries, and talent pool are real, and enormous effort has gone into taming it. If you must (or already do) run Java near the hot path, the techniques mirror this book's principles applied *against* the runtime:

- **Allocation-free / garbage-free Java.** The dominant technique: **don't allocate on the hot path** (Ch. 23 applied to Java) — because no garbage means no GC. Object pools (Ch. 24), pre-allocated and reused; primitive-typed flyweights over `ByteBuffer`s instead of objects; avoiding autoboxing, `Iterator`s, lambdas-that-capture, and the JDK's allocating APIs. A garbage-free hot path *never triggers* a young-gen collection — you sidestep the GC by never feeding it. This is the LMAX Disruptor's world (Ch. 37 — itself a Java library built exactly for this).
- **Off-heap memory.** Put hot data *outside* the GC's heap — direct `ByteBuffer`s, `sun.misc.Unsafe`/`MemorySegment` (the Foreign Function & Memory API, Java 21+), memory-mapped files (Ch. 26). Off-heap data isn't scanned or moved by the GC, giving C-like manual control (and manual lifetime risk — Ch. 72) within Java. Libraries like Chronicle (Queue/Map) build the Ch. 34/50/75 patterns (lock-free queues, shared-memory IPC, capture journals) off-heap in Java.
- **Pauseless / low-pause collectors.** **Azul Zing/Prime** (the C4 collector) is the canonical "pauseless" JVM — concurrent compaction that targets sub-millisecond (often sub-100µs) pauses even on large heaps, specifically marketed to and used by trading firms. OpenJDK's **ZGC**/**Shenandoah** chase the same goal. They don't make the GC *free* (barriers, throughput cost), but they cap the *tail* the §B.3 critique centers on — turning multi-ms pauses into sub-ms. Combined with garbage-free coding, the residual pauses become tolerable for some (not the lowest) latency tiers.
- **JIT warm-up mitigation.** Address the Ch. 46 / §B.3 warm-up problem by **warming the JVM**: run synthetic/shadow traffic at startup to drive JIT compilation *before* going live (Ch. 46's warming, applied to code compilation), use tiered-compilation tuning, or pin compilation. **GraalVM native-image** sidesteps it differently — **AOT-compiling** the Java application to a native binary with no JIT and no warm-up (and a different, smaller runtime), bringing Java much closer to the C++/Rust model (at some peak-throughput and ecosystem cost). Native-image + garbage-free + a region/epsilon GC approaches "Java without the two §B.3 problems."
- **The verdict:** taming the JVM is *real engineering that works* for the *upper* latency tiers (where sub-ms tails are acceptable), and it leverages a huge ecosystem. But it is *fighting the runtime* the whole way — every technique above is "how to use less of the JVM" — and at the very lowest tier (the FPGA/kernel-bypass tick-to-trade path, Ch. 62/69), the C++/Rust/C/Zig stack is still where you end up. Match the tool to the tier.

## B.5 FFI/interop with a C++ core; when a rewrite pays off

Real systems are **polyglot**: a C++ (or Rust) hot-path core, surrounded by other languages for the tiers that suit them. The engineering is the *boundary*:

- **Put the boundary at the latency tier line.** The order path / feed handler / risk core (Ch. 53, 55, 58, 61, 62, 74) in C++/Rust; the research, backtesting (Ch. 75–76), monitoring (Ch. 76), control plane, and UI in Python/Java/Go/whatever is productive. The capture/replay architecture (Ch. 74–75) *naturally* creates this seam — the deterministic core is C++, the analysis that consumes its captures is Python/Java.
- **FFI mechanics.** A C ABI is the universal interop layer (B.2): expose the C++ core through an `extern "C"` boundary; call it from Python (ctypes/cffi/pybind11), Java (JNI, or the modern Foreign Function & Memory API — Panama), Rust (`bindgen`, or native C ABI), Go (cgo). Rust↔C++ interop (cxx, autocxx) is increasingly smooth for mixed Rust/C++ codebases. **Keep the hot path on one side of the boundary** — an FFI *call per tick* into a different runtime (especially a GC'd one) re-introduces exactly the costs you split to avoid; the boundary is for *coarse* hand-offs (config, captures, control), not per-message hot-path calls.
- **Shared-memory interop beats call-based interop for data.** For high-volume cross-language data (capture streams, market data to a research process), a **shared-memory ring/journal** (Ch. 26, 50, 75) that the C++ core writes and another language reads is far better than FFI calls — it's the Ch. 74 process-topology pattern across languages, with no per-message FFI cost and clean fault isolation.
- **When a rewrite pays off.** Rewriting a working C++ hot path into Rust (or anything) is a large, risky investment — justify it with a *concrete* return: the borrow checker eliminating a recurring class of production memory-safety incidents (Ch. 72), a team-skills/hiring shift, or a greenfield component with no legacy. It rarely pays to rewrite *working, tuned, measured* hot-path C++ for its own sake — the Ch. 76 latency budget is already met, and a rewrite risks regressing it. It *can* pay for *new* components, for *unsafe-prone* parsers (Ch. 53, 72 — where Rust's safety is most valuable), or where the ecosystem/safety calculus has genuinely shifted. Decide with the same discipline as any optimization: measure the cost, name the return, don't rewrite on faith.
