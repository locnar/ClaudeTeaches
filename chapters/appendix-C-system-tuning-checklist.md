# Appendix C — System Tuning Checklist

> **Consolidates:** Ch. 6 (system setup), Ch. 16 (TLB/huge pages), Ch. 51 (context switching), Ch. 53 (thread/IRQ pinning), Ch. 54 (SMT), Ch. 55 (cache allocation / RDT), Ch. 56 (RT scheduling / kernel tuning), Ch. 59 (warming), Ch. 65 (socket/TCP tuning), Ch. 70 (NIC features), Ch. 72 (flow steering / receive scaling). This is the *operational* companion to those chapters: an ordered, copy-paste-oriented checklist for turning a stock Linux x86-64 box into a quiet, deterministic, low-jitter trading machine. Each item links to the chapter that explains **why**.

**How to use this:** work top-down — BIOS first (C.1), then kernel cmdline (C.2, requires reboot), then runtime knobs (C.3), then per-process (C.4), then *verify* (C.5). Lower layers gate higher ones: there's no point tuning `sysctl` if C-states still fire in firmware. **Measure before and after every change** (Ch. 3) — this checklist is a starting point, not a guarantee; the verification pass (C.5) is what proves the box is actually quiet. Values shown are sensible defaults for a single-socket trading box; adapt core numbers to your topology (`lscpu`, `lstopo`). Treat this as a template to version-control alongside the application, not a one-time ritual (Ch. 111 — tuning is defended continuously).

## C.1 BIOS/firmware (C-states, P-states/turbo, SMT, NUMA/snoop mode)

Firmware settings the OS can't override — set these first, in the BIOS/UEFI/BMC. **Why:** these are the deepest sources of jitter and frequency variation (Ch. 6); an un-tuned BIOS undoes everything above it.

- [ ] **Disable deep C-states** (allow only C0/C1; disable C1E, C3, C6+). A core waking from a deep sleep state takes microseconds — a cold-start stall on the first packet (Ch. 6, 59). Keep cores busy and shallow. *(Pair with kernel `intel_idle.max_cstate=1 processor.max_cstate=1` in C.2.)*
- [ ] **Fix P-states / disable frequency scaling and turbo variability** (Ch. 6). Either lock to a fixed high frequency, or disable Turbo Boost so the clock doesn't ramp/throttle unpredictably (turbo *raises* throughput but *adds* jitter as it engages/disengages and thermally throttles). For determinism, a *fixed* frequency beats a higher-but-variable one. Disable SpeedStep/Cool'n'Quiet.
- [ ] **Disable SMT / Hyper-Threading** (Ch. 54) — or plan to leave siblings idle (C.4). On hot cores, a sibling competing for front-end/execution/L1 is a jitter source; HFT hot cores usually run with HT off or the sibling empty (Ch. 54). Decide per the chapter; disabling in BIOS is the simplest.
- [ ] **NUMA clustering / snoop mode** (Ch. 17): enable NUMA (don't interleave/flatten in firmware — you want node locality visible to the OS). On Skylake-SP and later — including the Ice Lake-SP reference box — coherence is directory-based and there is no snoop-mode selector; the knob is **SNC (sub-NUMA clustering) on/off** plus the XPT/UPI prefetch options. Only on Haswell/Broadwell-EP boxes is it the *snoop mode* (Home Snoop vs Early Snoop vs Cluster-on-Die). Measure either way: SNC can lower local-access latency but splits each socket into two NUMA nodes, which complicates topology and pinning (Ch. 17). Disable node interleaving.
- [ ] **Disable unnecessary devices and their interrupts** (onboard audio, unused NICs/USB controllers, etc.) — fewer interrupt sources, fewer jitter sources (Ch. 53).
- [ ] **Disable power-management / "green" features**, set the firmware power profile to "maximum performance" / "low latency," disable processor power-capping (RAPL limits that throttle).
- [ ] **Power limits above the workload's reach, not "off"** (Ch. 57 §57.2.4, §57.4.4): PL1 = PL2 at the qualified maximum (`/sys/class/powercap/intel-rapl:0/constraint_{0,1}_power_limit_uw`), ICCmax at the vendor limit, BMC/Node-Manager/DCMI capping disabled; alarm on `thermal_throttle/{core,package}_{throttle,power_limit}_count` deltas (Ch. 106 §106.4.2). AMD: PPT/TDC/EDC at the SKU maximum, Determinism = Performance only for fleet uniformity (Appendix Q.7).
- [ ] **Uncore / fabric clock pinned** (Ch. 57 §57.2.5, §57.4.4): "Uncore Frequency Scaling = Disabled" (or min = max via `intel_uncore_frequency` / MSR 0x620); AMD: APBDIS = 1 + Fixed SOC P-state = P0, DF C-states disabled (Appendix Q.7). Verify with the first-L3-hit-after-idle test.
- [ ] **Turbo posture decided, not defaulted** (Ch. 7 §7.4.2): either turbo off at base (the Appendix L.3 posture) or a *pinned* ratio (min = max) qualified by a checksum-verified soak (Ch. 7 §7.4.3), recorded in the host fingerprint (Appendix M.2); `scaling_min_freq = scaling_max_freq`, EPP = `performance`, `hwp_dynamic_boost = 0` (Ch. 57 §57.4.3).
- [ ] **Sub-NUMA / NPS and L3-as-NUMA chosen for the box's role** (Ch. 18 §18.4.2): NPS4 / SNC on for the hot box with every hot process node-bound; NPS1 / SNC off for streaming capture/replay boxes; AMD "ACPI SRAT L3 Cache as NUMA Domain" on whenever the node count would otherwise hide the CCDs; `kernel.numa_balancing = 0` either way (C.3). Record the core-to-core map (Ch. 18 §18.3, Appendix L.7) with the deployment.
- [ ] **Hybrid parts: the hot partition is P-cores only** (Ch. 7 §7.4.4): `/sys/devices/cpu_core/cpus` ⊇ hot cores; E-cores host housekeeping; asserted at start-up.
- [ ] **Disable SMIs where possible** (System Management Interrupts — firmware can steal the core invisibly for ms; the worst hidden jitter). Disable thermal/legacy-USB SMIs if the vendor allows; some BMCs expose an "SMI-free" or "low-latency" profile.

## C.2 Kernel cmdline (`isolcpus`, `nohz_full`, `rcu_nocbs`, `intel_pstate`, `mitigations=`, huge pages)

Boot parameters (edit GRUB `GRUB_CMDLINE_LINUX`, `update-grub`/`grub2-mkconfig`, reboot). **Why:** these carve out cores the kernel won't disturb and set kernel-wide policy (Ch. 56, 16, 6). Assume hot cores are `2-7` and housekeeping is `0-1` (adapt to topology).

- [ ] **`isolcpus=domain,managed_irq,2-7`** (Ch. 56) — remove these cores from the kernel scheduler's general balancing (`domain`); only threads explicitly pinned there run. The foundation of a quiet core. The `managed_irq` flag (kernel ≥ 5.6) also keeps *kernel-managed* interrupts — multi-queue NIC and NVMe vectors — off these cores, which `irqaffinity=`/`smp_affinity` cannot do (C.3).
- [ ] **`nohz_full=2-7`** (Ch. 56) — tickless operation on the isolated cores: stop the periodic scheduler tick (the ~1000 Hz timer interrupt) when one task runs, eliminating that recurring jitter (Ch. 51, 56). Needs `CONFIG_NO_HZ_FULL`.
- [ ] **`rcu_nocbs=2-7`** (Ch. 56) — offload the *kernel's* RCU callback processing off the isolated cores onto the housekeeping cores, so kernel grace-period work doesn't fire on the hot core (unrelated to the user-space RCU of Ch. 44, though the grace-period idea is the same). Pair with `rcu_nocb_poll` if appropriate.
- [ ] **`irqaffinity=0-1`** — default IRQ affinity to the housekeeping cores so interrupts don't land on hot cores (Ch. 53; reinforce at runtime in C.3).
- [ ] **`intel_pstate=disable`** (or `=passive`) plus **`cpufreq` governor** management (C.3) — take fine frequency control, consistent with the BIOS P-state decision (Ch. 6). On AMD, the analog is `amd_pstate`. *(If you locked frequency in BIOS, ensure the kernel doesn't re-introduce scaling.)*
- [ ] **`processor.max_cstate=1 intel_idle.max_cstate=1`** (Ch. 6) — kernel-side enforcement of the shallow-C-state decision from C.1 (belt and suspenders). `max_cstate=1` still permits C1 (and C1E on some firmware), with a µs-scale exit on the first packet; add **`idle=poll`** (Ch. 6 §6.4, Ch. 59) to keep idle cores spinning in C0 so there is *no* C-state exit at all. The trade-off: more power and heat, and less turbo headroom for the other cores — pair it with a busy-poll design, and know that it supersedes the `max_cstate` knobs.
- [ ] **`mitigations=...`** (Ch. 6, 94) — the speculative-execution mitigation knob. On a **single-tenant, network-restricted, code-controlled** box (Ch. 53, 54, 56), the spec-exec mitigations (Spectre/Meltdown/retpoline — Ch. 6) can be a measured latency cost you choose to reduce (`mitigations=off`, or selectively). **This is a deliberate risk decision** (Ch. 94.4.4) given your threat model — not a default; document it, measure it (C.5), and only on a box whose attack surface justifies it.
- [ ] **Huge pages** (Ch. 16): reserve explicit huge pages at boot — **`default_hugepagesz=1G hugepagesz=1G hugepages=N`** (1 GiB pages for the largest mappings) and/or `hugepagesz=2M hugepages=M`. Boot-time reservation avoids fragmentation failures later (Ch. 16, 33). Decide explicit-vs-transparent (THP) per workload (THP knob in C.3).
- [ ] **`nosoftlockup nmi_watchdog=0`** — disable watchdog timers that periodically interrupt cores (Ch. 56 jitter).
- [ ] **`skew_tick=1`** — de-synchronize remaining ticks across cores so they don't all fire together (jitter smoothing).
- [ ] **`audit=0 selinux=0`** (if your security policy permits) — remove audit-subsystem overhead from the hot path; weigh against Ch. 94 requirements.

## C.3 Runtime knobs (governor, IRQ affinity/`irqbalance`, `tuned`, RPS/XPS, NIC ring/coalescing, `sysctl`, THP, `mlockall`)

Applied after boot (scriptable; put in a systemd unit / startup script, version-controlled). **Why:** the runtime-adjustable layer of Ch. 53, 65, 70, 16.

- [ ] **CPU governor → `performance`** (Ch. 6): `cpupower frequency-set -g performance` (every core), so cores don't downclock when "idle." Consistent with C.1/C.2 frequency policy.
- [ ] **Stop `irqbalance`** (Ch. 53): `systemctl stop irqbalance && systemctl disable irqbalance` — it would re-spread IRQs onto your hot cores. Then **pin IRQs to housekeeping cores manually**: for each device IRQ, write the housekeeping mask to `/proc/irq/<N>/smp_affinity`. Kernel-*managed* IRQs (multi-queue NIC/NVMe vectors, `PCI_IRQ_AFFINITY`) reject that write with `EIO` — for those, rely on `isolcpus=managed_irq` (C.2) and shrink the queue count so queues map onto housekeeping cores (`ethtool -L <if> combined <N>`). Pin the **NIC's** IRQs deliberately (Ch. 53, 70) — RX queues to the cores that will poll/process them (or onto housekeeping if busy-polling on the hot core, Ch. 60/70).
- [ ] **PM QoS held by the trading process** (Ch. 57 §57.2.2, §57.4.2): `/dev/cpu_dma_latency` opened with 0 for the process lifetime (the kernel drops the bound when the holder's fd closes — a restarted `tuned` is the classic silent regression), plus per-CPU `cpuN/power/pm_qos_resume_latency_us = 0` on the hot cores so housekeeping cores keep their deep states; the gate reads the device's *value*, not the profile name.
- [ ] **`tuned` profile** (optional): apply `tuned-adm profile latency-performance` (or `network-latency`/`realtime`) as a baseline, then layer manual tweaks. Convenient, but understand what it sets — don't let it fight your explicit choices.
- [ ] **NIC ring buffers and coalescing** (Ch. 67, 70): `ethtool -G <if> rx <N>` to size RX rings for microburst absorption (Ch. 67 — avoid hardware drops at the open); `ethtool -C <if> rx-usecs 0 adaptive-rx off` to **disable interrupt coalescing** for lowest latency (coalescing trades latency for throughput/CPU — wrong trade on the hot path, Ch. 70); `ethtool -K <if> gro off lro off` to **disable receive coalescing** (GRO/LRO *wait* to batch packets — Ch. 70 §70.2; keep `rx`/`tx` checksum offload on, Ch. 70 §70.3/§70.5); `ethtool -L <if> combined <N>` to match the queue count to the polling cores (receive scaling — Ch. 72); and confirm the NIC sits on the NUMA node of the cores that poll it (`cat /sys/class/net/<if>/device/numa_node` — Ch. 17, 70). Enable hardware timestamping (Ch. 70, 73) if used.
- [ ] **RPS/XPS** (Ch. 61 §61.2.2 and §61.4.2 for the mechanism — an RPS mask that names a hot core is an IPI plus a `NET_RX` softirq there; Ch. 70, 72): Receive/Transmit Packet Steering — steer packet processing to chosen cores. For a busy-polled kernel-bypass path (Ch. 77) this may be moot; for a kernel-stack path (Ch. 60), steer RX to the processing cores and keep it off hot cores you've isolated.
- [ ] **Disable Transparent Huge Pages (THP)** if using *explicit* huge pages (Ch. 16): `echo never > /sys/kernel/mm/transparent_hugepage/enabled` — THP's fault-time compaction and background `khugepaged` collapse are jitter sources (Ch. 16), and you've reserved explicit pages in C.2. *(If you rely on THP instead, set `madvise` and pre-fault — Ch. 16, 33.)*
- [ ] **Network `sysctl`** (Ch. 65): size socket buffers (`net.core.rmem_max`/`wmem_max`, `net.ipv4.tcp_rmem`/`tcp_wmem`), `net.core.netdev_max_backlog`, busy-poll (`net.core.busy_poll`/`busy_read` — Ch. 60, 70) for the kernel-stack path. Set `TCP_NODELAY` in the *app* (Ch. 65), not sysctl. For multicast market data (Ch. 65), size `net.core.rmem_max` generously, raise `net.ipv4.igmp_max_memberships` above the channel count, set `rp_filter=0`/`2` on the feed NICs, and verify a snooping querier exists on each feed VLAN (Ch. 69). (`net.ipv4.tcp_low_latency`, still found in older tuning guides, has been a no-op since the prequeue removal in kernel 4.14 — don't bother.)
- [ ] **VM / kernel `sysctl`** (Ch. 16, 17, 29): `vm.swappiness=0` (don't swap — Ch. 29/33), `vm.zone_reclaim_mode`, `vm.stat_interval` high (less vmstat housekeeping), and **`kernel.numa_balancing=0`** (or cmdline `numa_balancing=disable`) — stop automatic NUMA page migration and its hinting faults, a migration-stall/jitter source on a pinned, explicitly-placed hot path (NUMA — Ch. 17 §17.5). **Disable swap entirely** (`swapoff -a`) on a trading box — a swapped-out hot page is a multi-ms fault (Ch. 29, 33).
- [ ] **`mlockall`** (Ch. 33): have the application call `mlockall(MCL_CURRENT|MCL_FUTURE)` to lock all pages resident — no page faults, no swapping on the hot path (Ch. 29, 33). (This is application code, but it's the runtime memory-locking counterpart to the huge-page reservation.) Pre-fault and pre-touch (Ch. 59).
- [ ] **Turn off / pin background services** (Ch. 51, 56): cron, monitoring agents, `systemd` timers, log rotation, package-update daemons — confine them (and all non-hot processes) to the housekeeping cores via cgroup/`systemctl set-property AllowedCPUs`, or stop them. A surprise cron job on a hot core is a classic jitter incident.
- [ ] **`writeback`/dirty-page tuning** if the box does capture (Ch. 101): keep dirty-page writeback off the hot cores and on isolated storage (Ch. 101), so flushing doesn't stall.

## C.4 Per-process (affinity/`taskset`, RT priority, `numactl`)

Applied when launching the trading process(es) (Ch. 53, 56, 17). **Why:** pin the hot threads to the cores you isolated, give them RT priority, and keep their memory NUMA-local.

- [ ] **Pin hot threads to isolated cores** (Ch. 53): `taskset -c 2-7 <app>`, or — better — per-thread `pthread_setaffinity_np`/`sched_setaffinity` in the app so each hot thread owns exactly one isolated core (Ch. 53), one thread per core, never sharing. Keep housekeeping threads (logger consumer — Ch. 91, capture writer — Ch. 101, control plane) on the housekeeping cores (`0-1`).
- [ ] **Leave SMT siblings idle** (Ch. 54) if HT is *on*: pin only one thread per physical core and ensure the sibling logical CPU runs nothing (don't pin work to it; isolcpus + manual placement). If HT is off (C.1), moot.
- [ ] **RT scheduling priority** (Ch. 56): `chrt -f 80 <app>` (or `SCHED_FIFO`/`SCHED_RR` via `sched_setscheduler` per thread) so the hot thread isn't preempted by normal tasks. **Caution** (Ch. 56): an RT thread that busy-spins can starve kernel housekeeping on its core — combine with `isolcpus`/`nohz_full` (C.2) so there's nothing to starve, and set `kernel.sched_rt_runtime_us=-1` *only* on a properly isolated box (otherwise the RT throttle is a safety net you may want).
- [ ] **NUMA-local memory** (Ch. 17): `numactl --cpunodebind=0 --membind=0 <app>` to bind the process to one NUMA node's cores *and* memory, so allocations are node-local (Ch. 17 — cross-socket access is a latency penalty). For multi-socket boxes, place each hot process's memory on the node whose cores and NIC it uses (Ch. 17, 53, 70 — NIC-NUMA locality). First-touch the memory on the right node (Ch. 17).
- [ ] **Pre-fault and warm** (Ch. 59): at startup, touch all huge pages, prime caches/TLB/branch predictors with shadow traffic, establish connections — so the *first real tick* is warm (Ch. 59). This is application logic but belongs in the launch/readiness procedure.
- [ ] **FTZ/DAZ in every hot thread** (Ch. 34, Appendix D.3): set `_MM_SET_FLUSH_ZERO_MODE(_MM_FLUSH_ZERO_ON)` / `_MM_SET_DENORMALS_ZERO_MODE(_MM_DENORMALS_ZERO_ON)` (the MXCSR bits) in each hot thread's startup alongside affinity, and assert/log the MXCSR state — a thread that misses it is one underflow away from the 100× denormal cliff.
- [ ] **cgroup isolation** (Ch. 56): place the trading process in a cgroup with exclusive `cpuset` of the hot cores, and *all other* processes in a cgroup confined to housekeeping cores — enforcing the separation system-wide.
- [ ] **Cache allocation (Ch. 55):** `mount -t resctrl resctrl /sys/fs/resctrl`; `mkdir /sys/fs/resctrl/hotpath` and write a `schemata` that gives the hot cores **exclusive L3 ways** (e.g. `L3:0=f00`), shrink the default group to the *complementary* mask (`L3:0=0ff` — the masks must not overlap, §55.5) and add an MBA throttle for everything else; assign the hot cores via `cpus_list`; verify occupancy/bandwidth with CMT/MBM (`mon_data`). A pinned core without a cache partition still shares its L3 with every housekeeping thread (Ch. 55 §55.3).

## C.5 Verification pass (`cyclictest`, jitter measurement)

**Never trust the checklist — measure that the box is actually quiet** (Ch. 3, 56, 111). This pass is what turns "I set the knobs" into "the box is deterministic."

- [ ] **`cyclictest`** (Ch. 56): the canonical jitter measurement. Run pinned to a hot core, RT priority, for a meaningful duration under representative load: `cyclictest -m -p 80 -a 2 -t 1 -i 200 -d 0 -D 1h`. Read the **max** latency (the tail — Ch. 1), not the avg. A well-tuned isolated core should show single-digit-microsecond (often sub-µs avg, low-µs max) wake-up latency with a *tight* distribution; a fat max means residual jitter to hunt (an SMI, a missed isolation, a stray IRQ). Compare against an *un*-tuned core to see the improvement.
- [ ] **Hunt residual jitter sources** (Ch. 51, 56, 58): if `cyclictest` max is high, find the culprit — `rtla osnoise`/`timerlat` with stop-on-threshold tracing and the kernel noise catalog (Ch. 58), `perf sched`, `ftrace`, the `hwlat` detector (catches SMIs and hardware latency the OS can't see — Ch. 6's hidden firmware jitter), check `/proc/interrupts` for IRQs landing on hot cores (C.3), check for stray processes (`ps -eLo psr,...` to see what's on each core). Iterate until the tail is flat.
- [ ] **Prove the clock stayed flat** (Ch. 57 §57.3, §57.4.5): effective frequency per hot core from a housekeeping core (`APERF/MPERF` via `flatclock`/`turbostat --cpu 0-1`, or `perf stat -e cycles,ref-cycles -C <hot>`) = the pinned ratio ± 0.3 % all day; `thermal_throttle/*_count` static; hot-core C6 `usage` static (`cstates`); uncore at its pin; `/dev/cpu_dma_latency` reads 0. The first deviation is a named tail event, not a slower day.
- [ ] **Network softirq work stays off the hot cores** (Ch. 61 §61.2.2, §61.4.2): `NET_RX`/`NET_TX` columns in `/proc/softirqs` do not move for the hot CPUs; `softnet_stat` `time_squeeze` flat; `nft list ruleset` empty (or the hot ports `notrack`) and the conntrack module unloaded; no hot thread calls `sendmsg` on a kernel socket.
- [ ] **Verify the settings actually took:** C-states (`cpupower idle-info`), frequency/governor (`cpupower frequency-info`), isolation (`cat /sys/devices/system/cpu/isolated`, `/proc/cmdline`), IRQ affinity (`/proc/irq/*/smp_affinity`), huge pages (`/proc/meminfo` HugePages_*), THP (`/sys/kernel/mm/transparent_hugepage/enabled`), NUMA (`numactl -H`, `numastat`, `/proc/sys/kernel/numa_balancing` = 0), cache partition (`/sys/fs/resctrl/*/schemata`, `cpus_list`), mitigations (`/sys/devices/system/cpu/vulnerabilities/*`). A setting you *meant* to apply but didn't (a typo'd cmdline, a service that reset it) is the most common "why is it still jittery."
- [ ] **Measure the application's own tail** (Ch. 3, 111): `cyclictest` proves the *box* is quiet; the real test is the *application's* tick-to-trade distribution (Ch. 111) under a microburst (Ch. 67) — run the §111.3 decomposition and confirm the per-stage tails are flat. The box being quiet is necessary, not sufficient.
- [ ] **Re-verify after every change** (Ch. 111): a kernel update, a BIOS update, a config drift, a new background agent can silently re-introduce jitter. Bake this verification into a continuous sampler (Ch. 106 — the isolation counters diffed every second from a housekeeping core) and into the pre-trading-day readiness gate (Appendix M) — tuning is defended continuously, not set once.

## C.6 Configuration as code and drift detection

**Everything above is a declaration, not a memory.** A box tuned by hand decays (Ch. 106 §106.2.3): package updates re-enable `irqbalance`, a shared Ansible role flips `numa_balancing`, a BIOS update resets the C-state policy, an agent attaches a perf event to every CPU. The defence is to make the checklist an *artefact* — versioned with the release, applied by tooling, and audited against itself — and to let the sampler of Ch. 106 and the gate of Appendix M catch what the tooling cannot prevent.

- [ ] **Declare C.1–C.4 as code.** The kernel cmdline (a GRUB drop-in), the runtime knobs (a `sysctl.d` file, a `tuned` profile *you* own or none, a systemd unit tree for IRQ affinity / `ethtool` / `resctrl` / cgroups), the per-process launch (unit files with `CPUAffinity=`, `AllowedCPUs=`, `chrt`/`numactl` wrappers) — as an Ansible/Salt role (or equivalent) checked into the same repository as the trading system and **tagged with the same release**. Per-host differences (hot CPU list, NIC names, NUMA node, BDFs) live in one variables file per host; nothing else differs between siblings.
- [ ] **Inventory firmware too.** BIOS/BMC versions and their settings export (vendor `racadm`/`ilorest`/`redfish` dump), microcode revision, NIC firmware and driver versions, switch-port configuration for your ports (Ch. 75, Appendix K) — recorded in the release alongside the role, because C.1 is firmware and firmware is updated.
- [ ] **Generate the baseline fingerprint from the declaration** (Appendix M.2, Ch. 106 §106.4.4): the expected values of every check are derived from the role and the inventory, not typed by hand, so the gate compares the live box against *what the release says* and a mismatch has exactly two resolutions — re-apply the role (the box drifted) or change the role through a release (the intent changed, with a fresh Ch. 58 sign-off and baseline).
- [ ] **Audit continuously and at the gate.** The cheap subset — `effective_affinity_list` map, service states (`irqbalance`, `tuned`), the sysctl set, THP/governor/clocksource — is diffed against the declaration once a minute by the Ch. 106 sampler; the full attestation (cmdline/kernel/microcode/BIOS/firmware/NIC/PCIe/RDT) runs at boot and at T-60 (Appendix M.2). Any diff is a ticket with the knob named; a diff at T-60 blocks go-live.
- [ ] **Change the declaration, never the box.** No `sysctl -w`, no `ethtool -G`, no BIOS change outside a release — and when one is unavoidable in an incident, it is a *recorded* deviation that the next release either adopts or reverts. The baseline's history is the fleet's configuration log.
- [ ] **Re-sign-off after every declared change.** A new kernel, microcode or driver is a new box until Ch. 56's `cyclictest`, Ch. 58's `osnoise` run and the Appendix M.6 micro-suite say otherwise; the new baseline is recorded then, and only then.
- [ ] **The gate is the enforcement.** Appendix M turns this section and C.5 into a timed, scripted procedure with pass/fail criteria, run every trading day before the first order.
